## Quick answer

- What it is: Rolling ~7.5-day global map of IMERG rain and snow rate, one frame per 30 minutes; movies refreshed about every 30 min, frame files at :20 past the hour, data 4 to 6 h behind real time; NOT one image per day.
- Kind: data-animation
- Data source: IMERG (Integrated Multi-satellite Retrievals for GPM), near-real-time runs. VERIFIED from bundle: dataset credit 'IMERG', description 'provides precipitation rates for the entire world every 30 minutes'. INFERRED: the letter burned in the bottom-right corner ('L' on older frames, 'E' on the newest frames) marks IMERG Late run vs Early run. (observation)
- Period covered: Rolling window. At the 17:21 UTC snapshot: 2026-11-07T00:00Z to 2026-11-14T13:30Z = 364 frames x 30 min = 182 h = 7 d 14 h. At 19:20 UTC the newest was 14:30Z (366 frames) and it was still 14:30Z at 20:18 UTC (15:00Z returns 404). INFERRED: window starts 00:00 UTC seven days before the current UTC date; with a 4 to 6 h lag the count varies roughly 328 to 376 over a day (not 337 to 384). Rule seen on one day only.
- Time step of the underlying data: 30 minutes (file names step 1800 s with 0 gaps per dated_sets.json; on-screen labels confirm).
- **One frame equals**: 30 minutes of real time (one IMERG half-hour). Arithmetic: frame 0 label 2026/11/07 00:00:00, frame 128 label 2026/11/09 16:00:00 -> 64 h / 128 frames = 0.5 h; frame 256 label 2026/11/12 08:00:00 -> 128 h / 256 = 0.5 h; frame 360 (t=12.0 s) label 2026/11/14 12:00:00 -> 180 h / 360 = 0.5 h. At 30 fps: 1 s of movie = 15 h, one day = 48 frames = 1.6 s.
- **One frame = one day?**: no
- Where a program gets a frame's date: Best: file name (ISO 8601 UTC, e.g. 2026-11-07T00:00:00Z) in every frame set. Also: label burned into the 1080p movie and 1080p frames ('2026/11/07 00:00:00', bottom-left, would need OCR); the separate flatdates set (one small transparent PNG per frame containing only that white date text, for compositing); or the index formula above.
- Date label seen on screen: White bold text bottom-left 'YYYY/MM/DD HH:MM:SS' (e.g. '2026/11/14 13:30:00'). No time zone is printed; it equals the 'Z' (UTC) time in the file names, so it is UTC. The flatdates PNGs hold exactly this text on a transparent background (verified on imergert_dates.now.png: 339x63 RGBA, text '2026/11/14 14:30:00').

Late-run replacement of recent frames is INFERRED, not verified.

- What the colours mean: Liquid precipitation rate in mm/hour on a roughly logarithmic scale 0.1 to 50: green (light) -> yellow (about 1 to 3) -> orange -> red (10 to 50). Frozen precipitation (snow) rate in mm/hour, same ticks: light cyan (0.1) -> blue -> purple (50). No colour = below 0.1 mm/hour or no precipitation.
- Fit as a sonification source: **excellent** — A clean transparent data-only layer exists (no OCR, no masking of labels or background), every frame carries an exact UTC timestamp in its file name, geography is fixed on a flat map so pixel column = longitude and row = latitude, the colour scale has a clear physical meaning (rain vs snow, intensity in mm/hour), and there is both a live feed and a frozen June 2022 month for a demo that cannot break.
- Suggested mapping: Use flatalpha frames. For each frame, split the map into latitude bands (or a user-chosen region); count non-transparent pixels and classify hue: green-to-red = rain, cyan-to-purple = snow. Rain area drives the loudness of a rain-like noise layer, the share of orange/red pixels raises pitch or adds a low drum for heavy rain, snow pixels drive a separate soft bell timbre; pan left-right by longitude. Play 48 frames per day (e.g. 8 frames per second = one day in 6 s) and speak the date from the file name at each 00:00Z.

## Frame → time mapping

Frame sets: read the UTC timestamp straight from the file name, e.g. imergert_alpha.2026-11-14T13:30:00Z.png. Movie: time(i) = first_time + i x 30 min for i < N (N = number of data frames), where first_time = 00:00 UTC seven days before the render date (2026-11-07T00:00Z today); frames i >= N are a hold of the last data frame (about 1 s: 19:20 UTC render has 396 movie frames for 366 data frames = 30 held; bundle probe 392 for 364 = 28 held). Because the window moves, hard-coding first_time breaks after midnight UTC; get it from the folder listing instead.

## Gotchas

- NOT one frame per day: 48 frames per day. A 'daily' view needs you to pick or aggregate 48 frames.
- The window rolls: file names that exist now disappear after about 7.5 days (2026-11-06T23:30Z already returns 404). Never hard-code frame URLs for the live set; list the folder, or use the static hurricane2022 sub-folder.
- Newest data is 4 to 5 hours behind the render and the last few frames are re-rendered each hour; the newest frames are the Early run ('E') and are later replaced by Late-run ('L') versions (INFERRED from the corner letter and from old frames having Last-Modified about 15 h after their data time), so pixel values of the most recent ~14 h can change.
- The movie ends with about 1 second of held last frame (28 to 30 duplicate frames); frame index -> time is linear only for the first N frames.
- CORS: the server answers 'access-control-allow-origin: https://tempo.multiverse.music' for any Origin, so a page on localhost or your own site can display these images/videos but canvas getImageData / fetch() on them will fail. Download the frames and serve them from your own origin (or use a proxy).
- The bundle's page-size labels and counts are a snapshot: movie size, duration and frame count change every hour.
- flatdates PNG width varies with the text (bundle says 343x63; the 19:20 UTC now-strip is 339x63); the text is white on transparent, invisible on a white page.
- 1080p frames are 16:9, the 3600x1800 sets are 2:1: do not reuse pixel-to-lat/lon maths between them.
- Timestamp is the label of a half-hour; whether it marks the start or the end of the 30-minute accumulation is not stated on the page.
- Added by the second agent: A movie re-stamp does not mean new data. At 19:50 UTC the mp4, webm and now.png were rewritten with byte-identical sizes while the newest frame stayed 14:30Z (still true at 20:18 UTC). Do not use movie Last-Modified as a freshness signal; list the frame folder.
- Added by the second agent: The newest-frame lag is not constant: 13:30Z at the 17:21 render, 14:30Z at 19:20 (only 2 new frames in 2 h), unchanged at 20:18. Use the static hurricane2022 set, or frames at least 8 h old, for anything that must be reproducible.

##### Media group 338067 | widget: Basic text with HTML | title: (none)
Description: The Global Precipitation Measurement (GPM) mission produces NASA's most comprehensive global rain and snowfall product to date, called the Integrated Multi-satellite Retrievals for GPM (IMERG). It is computed using data from the GPM constellation of satellites — a network of international satellites that currently includes the GPM Core Observatory, GCOM-W1, NOAA-18, NOAA-19, DMSP F-16, DMSP F-17, DMSP F-18, Metop-A, and Metop-B. The global IMERG dataset provides precipitation rates for the entire world every 30 minutes. Although the process to create the combined dataset is intensive, the GPM team creates a preliminary, near-real-time dataset of precipitation within several hours of data acquisition. This visualization shows the most currently available precipitation data from IMERG, depicting how rain and snowstorms move around the planet. As scientists work to understand all the elements of Earth's climate and weather systems, and how they could change in the future, GPM provides a major step forward in providing comprehensive and consistent measurements of precipitation for scientists and a wide variety of user communities.
